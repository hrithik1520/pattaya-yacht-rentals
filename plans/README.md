## Execution notes (what actually happened)

All three executed directly (not via isolated worktree subagents, since they're small and independent) and verified against each plan's own feel-check section with real headless-Chrome measurements, not just visual inspection.

**Plan 003 surfaced a real bug during execution** that the plan itself didn't anticipate: the originally-specified `#mobileMenu { display: grid; ... }` rule (an ID selector) had higher CSS specificity than Tailwind's `.md:hidden { display: none }` (a class selector), so the mobile menu stayed visible at desktop widths too — regardless of source order, ID beats class. Fixed by scoping the grid/transition rule inside `@media (max-width: 767.98px)` so it never competes with `md:hidden` at desktop at all. A second, smaller issue also surfaced: the closed state measured ~33px instead of ~0px because the grid item's own padding survived even with `overflow:hidden` + `min-height:0` (padding is intrinsic to the box, not clipped content) — fixed by moving the padding one level deeper so the direct grid item has zero intrinsic size. Both fixes are reflected in the current code and in `plans/003-mobile-menu-transition.md`'s Target section.

Plans 001 and 002 executed and verified with no deviation from their written Target sections.

## Recommended execution order

**No hard dependencies between these three plans** — they touch different, non-overlapping code paths (button CSS, contact form JS, header/nav JS+CSS) and can be executed in any order, including in parallel by different agents.

If executing sequentially, suggested order is by how quickly each can be verified:

1. **001** first — smallest scope (one CSS file, three rule blocks), fastest to verify, and establishes the `cubic-bezier(0.23, 1, 0.32, 1)` ease-out curve as the value to reuse.
2. **003** second — self-contained to the header component, moderate scope.
3. **002** last — largest scope (rewrites three JS event handlers plus new CSS), most important to get right since it's the primary conversion flow; benefits from doing it once other motion on the site already uses the same easing curve for a consistent feel.

## Notes for whoever executes these

- All three plans independently specify the same `cubic-bezier(0.23, 1, 0.32, 1)` ease-out curve as a literal value (this repo has no shared token file for easing yet — see the audit's finding #5, "Weak/duplicated easing tokens," which was flagged but not turned into a plan in this round). If you execute all three, the site converges on one consistent curve even without a shared token existing yet. A future plan could extract this into a `--ease-out` custom property once it's used in enough places to be worth centralizing — do not do that as a side effect of any of these three plans; each explicitly forbids introducing a token file to stay in scope.
- After executing any plan, run `node check_console.js` from the project root (with the local server running via `python3 -m http.server 8080`) to confirm no console errors or broken pages were introduced.
- Two additional findings from the audit were not turned into plans this round (user selected the top 3 by leverage): ungated `:hover` motion causing sticky-hover on touch devices (MEDIUM, affects most `.card`/`.dark-card` hover effects sitewide), and the FAQ `<details>` disclosure having no reveal transition (MEDIUM, affects `faq.html` and every yacht/destination page). Ask for these to be planned next if wanted.
